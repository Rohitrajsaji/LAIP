## Current boundary and migration objective

The prototype remains single-user localhost Compose, with a shared backend service credential, configured system namespaces, PostgreSQL and private local artifact volumes. [Settings](../backend/src/laip/config.py), [REST authentication](../backend/src/laip/read_api.py), [analyst authentication](../backend/src/laip/analyst_api.py) and [browser Host/Origin guards](../web/src/lib/analyst-policy.ts) establish this boundary. They do not establish enterprise users, tenants or per-user source grants. Browser pairing in the [architecture](laip-architecture.md) is a design, not evidence of implemented identity. Existing audit records are not independently tamper-evident. There is no implemented OIDC, live connector credential store, S3 backend or Kubernetes deployment. Optional private AI configuration does not establish enterprise approval controls. [Step 15](laip-step-15-validation.md) proves only its recorded offline checks.

The enterprise migration must preserve immutable artifact hashes, entity IDs, namespace identities, evidence, snapshots, rule revisions and review history. A system namespace identifies a source system; it must not be reinterpreted as an organization or tenant. Add an explicit organization ownership mapping and policy model through reviewed database/API migrations. Existing rows require an operator-approved ownership manifest; ambiguous ownership blocks publication. No network exposure is authorized by this document.

## Identity, authorization and source access

Proposed browser login uses a server-side BFF with Authorization Code flow, PKCE S256, state and nonce, exact registered redirects, secure HttpOnly cookies, session expiry, CSRF protection and server-side token storage. Identify a person by issuer plus subject, never mutable email. Validate signature with an approved algorithm/JWKS, issuer, audience, expiry and applicable nonce/authorized-party requirements. APIs require their own audience-bound access token or a validated internal delegation; an ID token is not an API credential. Use administrator-controlled issuers and endpoints, bounded key caches and rotation tests, and deny unvalidated tokens during identity-provider failure. These choices follow [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html) and [OAuth security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html); LAIP authorization remains a separate design.

Introduce typed `Principal`, `OrganizationScope`, `SourceGrant`, `PolicyDecision` and `WorkloadIdentity` interfaces. `authorize(principal, action, resource, policy_version)` returns allow/deny and an auditable reason before repository/blob access. Map approved identity-provider claims to local role assignments; do not trust arbitrary groups, request namespaces or forwarded user headers. Organization membership and source grants are mandatory in addition to action permissions. Machine identities have separate short-lived credentials and narrowly scoped delegation; the current shared token cannot impersonate enterprise users. Logout, disabled accounts, grant removal and role changes invalidate sessions, policy caches and queued delegations within a documented maximum delay.

The selected identity profile must also specify refresh-token rotation/reuse handling and measured revocation bounds; avoid indefinite sessions when the identity provider is unavailable. Repository operations require explicit organization/source scope; choose and test database enforcement such as row-level security as defense in depth, including owner/service-role bypass behavior. Database contents, temporary storage and backups carry sensitive evidence and require approved encryption at rest and separated administrative access, alongside object-store encryption.

Roles are proposed permission bundles, not a hierarchy. No role automatically inherits source access or another role's permissions. Administrative configuration authority does not confer source-read authority.

| Role | Proposed action permissions | Additional source/policy gate |
| --- | --- | --- |
| Administrator | Identity/role policy, approved endpoint and retention configuration | Separate audited grant for source; destructive policy changes require designated approval |
| Operator | Import/run/cancel, scoped connector operation, recovery | Approved collection scope and delegated artifact access; no secret-value read permission |
| Analyst | Inventory, authorized evidence/source, exact/keyword/graph/context retrieval, source-excluded exports | Metadata and evidence can contain source; enforce their grants too |
| Reviewer | Rule approve/reject/correct with immutable revisions | Access to every supporting artifact; unresolved or changed basis cannot be verified automatically |
| Auditor | Redacted audit/provenance reports | Source access separately granted; audit permission does not expose source text |

Separate permissions include `source.read`, `review.write`, `export.create`, `export.source`, `connector.manage`, `connector.collect`, `ai.use`, `ai.approve`, `retention.configure` and `retention.execute`. Proposed names are not current API scopes. Require explicit full-source export permission and the existing explicit option. Source-excluded exports still require authorization for embedded evidence, names and rule descriptions.

Enforce policy in shared services used by REST, read-only MCP and workers, including graph endpoints, edge names, counts, search snippets, evidence spans, historical revisions, source downloads, export creation/download and error bodies. Filter before retrieval ranking and before context/model transmission, not only at response rendering. Cache keys include organization, principal/grant fingerprint, snapshot and policy version. Partition and filter embeddings, chunks and vector candidates; their contents remain sensitive derivatives. Avoid revealing inaccessible object existence through errors or aggregate counts. No new MCP mutation or command surface is proposed.

Durable jobs store actor, organization, approved scope and policy version but never bearer tokens. Revalidate at claim, sensitive read, model transmission and publication/download. Revocation cancels or restricts in-flight work and invalidates derived caches/exports; a prior enqueue decision is insufficient. A result spanning several artifacts uses the combined restrictions of its supporting artifacts. Policy changes affect authorization without altering historical evidence/review records; inaccessible evidence cannot justify a currently verified view.

## Connector secrets and approved private AI

`SecretResolver.resolve(reference, workload, purpose)` is a proposed server-only interface backed by an approved secrets provider. Persist opaque secret references and encrypted credential versions; use envelope encryption with separately managed KMS keys, authenticated context binding to organization/connector, minimal decrypt grants and rotation/revocation procedures. Never place cleartext credentials in job payloads, provider descriptors, database diagnostics, URLs, logs, evidence, browser state or exports. Secret values exist only in bounded worker memory and private secret mounts where necessary. Encrypted backups require recoverable keys under separate access control; key destruction must account for restore obligations and legal holds.

Before implementation, select the actual secrets provider and key service, validate TLS and workload identity, and test cross-organization reference substitution, rotation during collection, provider outage, redaction and compromised-worker scope. Kubernetes Secrets alone do not establish encrypted storage: explicitly configure encryption at rest and restrictive RBAC, including list/watch access. See [Kubernetes secret practices](https://kubernetes.io/docs/concepts/security/secrets-good-practices/).

AI stays off by default. Approved private endpoints require a recorded owner, endpoint/TLS identity, model/tokenizer/dimension pins, allowed organizations/artifact classifications, retention/training terms, data residency, egress allowlist and expiry. `AIApprovalPolicy` authorizes both embedding and generation requests after source filtering. Recheck approval before sending data; never fall back to another endpoint or download a model. Prevent redirects/DNS changes from bypassing the approved network destination. Keep prompts and source out of routine logs. Treat imported instructions as inert data, enforce token budgets and validate citations against selected authorized evidence. Model output cannot resolve unknown paths, fabricate citations or grant review approval. Separate deterministic retrieval tests from semantic/model acceptance; revocation requires removal or isolation of affected vector/cache derivatives and downstream provider deletion evidence where applicable.

## Audit, storage and retention

`AuditSink.append(event)` records principal/workload, organization, policy version, request/job correlation, action, scoped resource, decision, outcome, timestamp and redacted reason. Include denied access, source reads, role/grant/secret-reference changes, AI approvals/transmissions, review revisions, imports, exports/downloads, cancellation, retention and restores. Never log raw source, prompts, tokens or credential values. Proposed enterprise audit requires append-only central collection, integrity verification/checkpoints, restricted deletion and independently retained administrative events; a hash chain inside the same writable database alone does not prove tamper resistance. Define maximum audit-outage backlog and alerts. Security-critical mutations/publication, protected source reads/downloads and AI transmissions require durable audit acceptance before commit, disclosure or transmission; a bounded durable outbox is acceptable. Fail closed when durable recording cannot be guaranteed; denied requests remain denied even if the sink fails. Test audit-outage handling on these paths, outbox recovery, duplicate delivery and immutable correlation with committed operations.

Proposed `ArtifactStore` exposes bounded put/read/stat/delete-by-version and checksum verification, not arbitrary bucket operations. Use private S3-compatible endpoints, TLS, narrowly scoped service identities, encryption with approved keys and organization-scoped opaque keys. Content hashes prove byte identity, not authority; avoid global cross-organization deduplication or observable existence probes. Preserve multiple authorized occurrences/provenance even when bytes coincide within a scope. Complete and verify an immutable upload before transactionally publishing its DB reference; use a staging ledger and grace-period orphan collector for crashes. Denied/deleted artifacts must not remain accessible through object URLs, caches or exports. Prefer authenticated download proxying; any future signed URL needs bounded lifetime and an explicit revocation limitation accepted by policy.

Store LAIP's SHA-256 independently of storage ETags and verify full downloaded bytes. Multipart and encryption can change ETag semantics; [AWS object metadata](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html) does not make an ETag LAIP's checksum. Validate the selected endpoint's checksum behavior using [S3 integrity documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html). Compatibility tests must cover conditional writes, exact version reads/deletes, pagination, multipart abort, private access, encryption, failures and publication recovery. AWS documentation is a reference, not proof that another S3-compatible store implements the same features.

Retention policies separately cover inputs, snapshots, evidence, reviews, chunks/vectors, generated exports, staging, audit and backups. Configure duration, organization ownership, legal hold, active-job/pin exclusions and deletion authority. A reviewed deletion plan identifies dependencies, retires coherent knowledge scopes and invalidates derived views before reference-checked blob removal. Preserve required redacted tombstones; never label a rule verified after deleting its supporting basis. Recheck grants, holds and references under concurrency before deletion. Record partial failures and retry idempotently. Organization termination must account for every object version and derivative.

Versioning makes deletion more complex: ordinary object deletion can create a marker while versions remain. [S3 DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html) and [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html) distinguish version deletion, retention and holds. Do not promise immediate erasure while holds or backup retention apply. Use storage-native locks only after validating actual provider support; a missing required lock is a deployment blocker. Never automatically bypass governance retention. Backup expiry and key retention are explicit schedules, not consequences of primary-store deletion.

## Kubernetes and operational compatibility proposal

No manifests, Kubernetes certification or production availability are delivered. Proposed API/BFF and worker workloads use pinned images, non-root users, read-only root filesystems where compatible, dropped capabilities, resource limits and restricted pod security. Disable unnecessary service-account token mounting; grant workload identity only to components that need it. Private ClusterIP services and an authenticated TLS ingress replace localhost only after the gates below; DB, object storage, workers and health endpoints must not acquire public bindings. Enforce ingress/egress policy for DB, secrets, identity, approved source systems and approved AI with a network implementation that actually enforces it. [Kubernetes security guidance](https://kubernetes.io/docs/concepts/security/) and [NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/) inform these requirements.

Separate liveness from readiness; readiness requires compatible DB schema, accessible private storage and required policy dependencies. Liveness should not create cascading restarts during a database outage. Workers use existing durable-job leases/fences rather than in-memory ownership; test duplicate claims, eviction, termination grace, cancellation and stale publication. Apply migrations through one controlled job before compatible services become ready. Rolling upgrades need an explicit schema/API compatibility window; drain incompatible workers. Multi-replica correctness, cluster versions/CNI/storage class, secret provider, S3 endpoint and PostgreSQL/pgvector versions all require a recorded tested matrix. Pod disruption controls do not replace backup or prove availability.

Back up DB, referenced immutable blob versions, ownership/policy configuration, schema/provider pins and recoverable secret-key references at a consistent watermark. Restore into an isolated environment; verify hashes, provenance/foreign keys, grants, audit continuity and review history; fence old workers and suspend stale jobs. Reassess AI/connector approvals before reactivation. Define and measure RPO/RTO, capacity, quotas, audit lag, job recovery and monitoring; do not assign untested promises. Rollback must preserve writes or use a controlled freeze/restore procedure approved against data loss. A failed migration cannot silently expose unowned legacy rows or reuse the prototype credential as enterprise authentication.

## Implementation backlog and release gates

All gates below are **NOT IMPLEMENTED / NOT VALIDATED for enterprise deployment**. Documentation acceptance is separate from runtime release acceptance. Owners are proposed accountable roles, to be assigned before work starts.

| Gate | Owner | Required implementation and acceptance evidence |
| --- | --- | --- |
| ENT-01 Ownership/migration | Architecture + data owner | Approved organization/source ownership manifest; stable IDs/hashes/revisions; orphan/ambiguous ownership denied; dry-run migration and rollback |
| ENT-02 Identity | Identity engineer | Approved issuer/access-token profile; invalid issuer/audience/signature/nonce/expiry and forged delegation rejected; key rotation, logout, outage and revocation tests |
| ENT-03 Authorization | Application security | Role/source matrix enforced across REST/MCP/jobs/DB/blob access; cross-organization ID, graph/count, snippet, historical revision and export leakage tests; stale queued/in-flight grants denied |
| ENT-04 Secrets/AI | Security + connector owner | Encrypted secrets provider and scoped workload access; rotation/outage/redaction; model/endpoint approval and revocation; no unauthorized egress/fallback; injection and unsupported-citation tests |
| ENT-05 Audit/storage/retention | Security + storage owner | Central integrity-checked audit; audit-outage denial before protected reads/downloads, mutations/publication and AI transmission; durable outbox recovery; DB/object atomic publication recovery; checksum/version matrix; hold/deletion/race/derivative/backup accounting; download revocation tests |
| ENT-06 Recovery | Operations + data owner | Isolated coordinated restore preserving IDs/evidence/reviews/grants; missing/corrupt blob behavior; stale-worker fencing; measured RPO/RTO and tested rollback |
| ENT-07 Cluster compatibility | Platform operations | Pinned target Kubernetes/CNI/storage/DB matrix, restrictive workloads and network policy; migration/rolling update/eviction/resource failure tests; private service and TLS checks |
| ENT-08 Release authorization | Security + product/data owner | Completed threat review, multi-user/organization tests and penetration assessment; assigned support/incident/retention owners, runbooks, monitoring and controlled rollout approval |

Implement in gate order, with ENT-03 required before any multi-user exposure and ENT-04–07 before sensitive live collection or production deployment. Block rollout on unresolved authorization, source leakage, key recovery or audit integrity findings. Readiness depends on implemented controls and recorded validation against the selected deployment. The prototype remains localhost and AI-disabled during this roadmap work.
