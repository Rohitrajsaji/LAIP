# LAIP step 17 — expanded IBM i language and analysis roadmap

Recorded 2026-10-08 for [execution-plan step 17](plans/laip-execution.md#step-17). This is a P1 design and backlog milestone. SQLRPGLE, fixed-format RPG, RPG III, IBM i COBOL, richer binding, field lineage and cross-program rule analysis are **not implemented or validated by this document**. Application modernization and code translation are outside scope.

## Current boundary and architecture decision

The [step-8 validation](laip-step-8-validation.md), [parser decision](rpgle-parser-decision.md), [parser](../backend/src/laip/rpgle_parser.py), [origin mapping](../backend/src/laip/rpgle_source.py) and [IR builder](../backend/src/laip/rpgle_ir.py) establish a bounded free-format Python/Lark analyzer. Unknown statements and invocations, unresolved includes and unsupported effects block conclusions. Existing CL/DDS analysis and synthetic customer validation do not establish these new language capabilities.

Retain the user-selected LAIP-owned Lark grammar and locked Lark 1.3.1. The earlier [REA assessment](rea-assessment.md) reuse gate was superseded by that explicit step-8 selection; there is no claimed upstream spike failure. Future reuse evaluation may inform isolated extension parsers, but does not silently replace the current parser. Shared identity, evidence, IR, retrieval and export contracts remain platform independent; IBM i dialect rules belong in versioned provider profiles. Schema 0.1.0 remains unchanged until a separately reviewed versioned extension is necessary.

The extension boundary is accepted artifacts plus an immutable configuration, producing diagnostics, facts, evidence, private IR and declared coverage through the existing fenced analysis publication path. Proposed implementations must use the current durable jobs, cancellation, digest verification and bounded artifact access. Parser dependencies cannot fetch includes, run imported code, invoke compilers or precompilers, or collect remote metadata. Live collection belongs to the separately gated [connector milestone](laip-step-16-connector-milestone.md).

P1-A precedes SQL-derived lineage; P1-B and P1-C have independent format gates. P1-D can proceed independently after its parser/licensing gate. P1-E must establish object/source correspondence before binding can refine resolution. P1-F and P1-G require supported language/effect summaries, not merely additional parsed files. Each stage can ship partial declared coverage without widening existing claims.

IBM documents [ILE RPG embedded SQL requirements](https://www.ibm.com/docs/en/i/7.5.0?topic=programming-coding-sql-statements-in-ile-rpg-applications), including differences from compiler support; LAIP therefore cannot treat generic RPG recognition as SQL precompiler equivalence. The [ILE RPG reference](https://www.ibm.com/docs/it/ssw_ibm_i_76/pdf/sc092508.pdf) and [IBM RPG/400 reference guidance](https://www.ibm.com/docs/en/i/7.6.0?topic=rpg-related-information) establish separate reference surfaces; obtain the actual RPG/400 manual before finalizing cycle/opcode semantics. IBM's [ILE COBOL Programmer's Guide](https://www.ibm.com/docs/en/ssw_ibm_i_76/pdf/sc092540.pdf) supplies the IBM i reference baseline. These publications inform the proposal; they do not prove tested compatibility on 7.5, 7.6 or an older compiler.

## Common contracts and uncertainty

Every new profile retains canonical namespace and qualified identity; equal object/member/field names across libraries stay distinct. Preserve source hashes, raw byte ranges, decoded coordinates and include/replacement origin chains. Source-derived observations and collected object bindings carry different method/time/authority evidence. Source-to-object mismatch remains explicit rather than choosing the newest observation silently.

IR extension proposals must version nodes/effects and declare unknown effects. Retrieval must retain diagnostics and supplied-artifact accounting, expose partial analysis, and refuse to turn absence of a parsed edge into absence of a dependency. Existing evidence certainty and analyst review are independent: a static derived relation can remain unreviewed; an unresolved target remains unresolved even after a reviewer adds a hypothesis. Corrections create immutable revisions and changed supporting evidence invalidates prior approvals. API/MCP/export consumers receive the same versioned facts and evidence, with full source still requiring the explicit option and applicable access policy.

## Measurable conformance and unsupported reductions

There is currently no audited numeric baseline for these proposed dialect corpora. Do not infer one from step-8 test counts or report an invented reduction percentage. Before implementing each stage, freeze a licensed corpus manifest with artifact SHA-256, dialect, source format/encoding, compiler reference, include/metadata completeness, expected supported facts and known unsupported constructs. Keep synthetic and real-source results separate.

Record, by dialect and construct category: supplied artifacts; analyzed/partial/rejected artifacts; total expected constructs; supported constructs; opaque/barrier constructs; missing/ambiguous includes; unresolved/ambiguous references; evidence-span mismatches; erroneous supported facts; false verified conclusions; and execution/fetch attempts. Define unsupported rate as barrier constructs divided by expected constructs on the same immutable corpus and counting rules. Record baseline B and candidate C, then absolute reduction B−C; publish relative reduction only when B is nonzero. New corpus additions use a new baseline. Do not reduce barriers by dropping artifacts, suppressing diagnostics or promoting unknown effects.

Each stage's acceptance requires all declared fixture facts and spans to match, no regression in the existing bounded suite, zero unsupported claims promoted to supported/verified, zero imported execution/network fetch, explicit resource/cancellation outcomes and deterministic replay without duplicate publication. A reduction target must name the construct categories moved into support and their corpus denominator before work begins; a lower unsupported rate alone is insufficient.

Real-source support additionally requires an authorized representative corpus for every advertised dialect/format/compiler profile, reproducible independent expected results, owner-reviewed metadata correspondence and documented redistribution/access limits. Optional existing compiler listings may be supplied as corroboration with provenance; this milestone never runs compilers against customer code. IBM i live queries and authorities require the separate connector validation gates. Until those prerequisites are met, status is **synthetic subset evaluated** or **untested**, never full language or live platform support.

## Handoff and release gates

1. Freeze corpus, licensing, target profile and unsupported baseline; retain denied/missing material in accounting.
2. Complete isolated parser comparison and immutable dependency pin/notice inventory; choose the smallest justified subset in an ADR.
3. Specify versioned facts/effects and schema compatibility, then implement only in a separately authorized milestone with tests first.
4. Validate spans, barriers, origin expansion, CFG/data flow, review invalidation, retrieval/export parity, replay and cancellation.
5. Obtain real-source and metadata validation for each claimed profile; publish a coverage matrix with explicit exclusions and remaining barriers.

This roadmap supplies the step-17 design acceptance material. Runtime implementation, parser spikes, real-source corpus validation and live authority validation remain future work. The [enterprise milestone](laip-step-18-enterprise-milestone.md) and [provider extensions](laip-step-19-provider-extensions.md) retain their own implementation and validation gates.
